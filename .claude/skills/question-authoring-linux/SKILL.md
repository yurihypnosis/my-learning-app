# Linuxの教科書（図解ドリル）

**先に `question-authoring`（共通ルール・適用手順）と `explanation-clarity`（わかりやすさの方法論）を読むこと。ドリルの型は `question-authoring-stats` を完全に踏襲する（viz・calc・大量生産の型はすべてそちら準拠）。** ここは本ドリル固有の情報だけ。

## この問題集の性格

資格試験対策ではなく**教養ドリル**。読者はソフトウェア品質保証（QA）畑6年の社会人で、Linux・コンテナ技術には知識ゼロに近い苦手意識がある（[[user_career_background]] 参照。このファイルはメモリではなくスキル内の参照コメントなので、実体は memory ディレクトリを見ること）。

- **目的はコマンドの丸暗記ではなく「なぜそう動くのか」の本質理解。** `ls -la` の意味を覚えさせるのではなく、「ファイルシステムとは何か」「プロセスとは何か」「シェルはただのプログラムである」という仕組みの理解を主役にする
- 参考文献: 『新しいLinuxの教科書』（三宅英明・大角祐介、SBクリエイティブ）の章立て・視点を土台にする（シェル・ファイルシステム・プロセス・標準入出力とパイプ・権限・環境変数など、コマンド一覧ではなく概念の理解を軸にした構成で知られる本）
- **解説は小学生でも分かるレベルに振り切る**（stats-basics/G検定と同じトーン）。ただし読者は大人なので漢字は普通に使う
- **全問に `viz`（1枚の図解SVG）を付ける。** コンピュータの中で今何が起きているかを目で追えることがこのドリルの価値
- QAエンジニアとしての実務接点があれば `usecase` や `eg` で拾ってよい（例: 自動テストのログをパイプで絞り込む、CI環境のシェルスクリプトを読む、Dockerコンテナでテスト環境を再現する）。ただし無理にこじつけない
- 将来の学習ロードマップ（GCP ACE / CKA）の土台にもなる領域なので、「後で出てくる用語」を先取りで自然に張っておいてよい（例: namespace/cgroupの回でコンテナオーケストレーションに軽く触れる）

## 問題の形

- 4択 single。問題文は1〜3文。**身近な比喩か、QAエンジニアが実務で遭遇しそうな場面**から入ってよい（CIのログが変、テスト環境のコンテナが動かない、権限エラーで自動テストがコケた、など）。無理にシナリオ化せず、素直な「〜はどれか」でもよい
- 誤答は「隣の概念」を置く（プロセスを問うならスレッドやプログラムを置く、SIGTERMを問うならSIGKILLを置く）。共通ルールの長さ縛り（正解を単独最長にしない）を厳守
- `code` 列は基本使わない。コマンド例を見せたいときも「見せて覚えさせる」のではなく `think` や `eg` で仕組みを言葉に開くことを優先する。どうしてもコマンド例が理解の助けになる場合のみ `snippet` に短く置く（暗記させるためではなく、仕組みの確認用）

## 解説の流儀

stats-basics と同じキー構成:

| 要望 | キー |
|---|---|
| 何がどういう意味か | `asked` + `kid`（ざっくり言うと） |
| たとえで直感 | `eg`（一番力を入れる） |
| なんのためにあるか | `why_asked`（「この仕組みが無いと何に困るか」） |
| どういうことに役立つか | `usecase`（実務・日常の場面。QA/CI/自動化と繋がるなら拾う） |

加えて `point`・`terms`（2〜4個）・`think`（因果の背骨）・`vs`（隣接概念との違い。「プロセス vs スレッド」「SIGTERM vs SIGKILL」「コンテナ vs VM」など）・`opt`・**`viz`（全問必須）**。

## viz（図解SVG）の書き方

`question-authoring-stats` の「viz（図解SVG）の書き方」節に完全準拠（viewBox・配色・PNG目視検証手順すべて同じ）。Linuxドリル固有の定番の型:

- 層構造（ハードウェア→カーネル→ユーザー空間のような積み木）
- 木構造（ディレクトリツリー、枝分かれ）
- 箱と矢印（親プロセス→子プロセス、コマンド→PATH探索→実行ファイル）
- パイプの流れ図（コマンドA → 矢印 → コマンドB、データが左から右に流れる）
- 2列比較（VMとコンテナ、SIGTERMとSIGKILL、絶対パスと相対パス）
- 同心円/仕切り（namespaceで見える範囲を仕切る、cgroupで資源を仕切る）

## 内容の注意

- **コマンドの列挙・暗記を目的にしない。** 「このコマンドを打つと何が起きているか」を問う。逆に「このオプションは何の略か」のような暗記チェックは避ける
- ディストリビューション差分（Debian系 vs RedHat系のパッケージ管理など）は本質理解が済むまで扱わない。土台のカテゴリが揃うまで後回し
- 「なぜこの仕組みがあるのか」を必ず1つは書く（例: 権限が無いと何が困るか＝他人のファイルを誰でも消せてしまう）。これが「本質を理解する」というユウの要望の核
- コンテナ回は「VMとの違い」を必ず `vs` で拾う。ここが一番の誤解ポイント（コンテナ＝軽量なVM、ではなくnamespace/cgroupによるプロセスの隔離）
